# AI Copilot - Architecture (MVP)

Status: proposal for review (end of Phase 0).
Inputs: product requirements (spec), `docs/phase-0/platform-investigation.md` (referenced below as "PI x.y").

Principles are named where they drive a decision: SRP, OCP, DIP, DRY, KISS, YAGNI.

---

## 0. Key decisions at a glance

| Decision | Choice | Why |
|---|---|---|
| Backend stack | Java 25, Spring Boot 4.1 (Spring MVC + virtual threads), PostgreSQL, Flyway, Spring `JdbcClient` | Owner's main stack. Explicit SQL makes atomic state transitions and uniqueness guarantees visible (KISS). |
| Build | Maven, single module | One deployable, no multi-module ceremony (KISS, YAGNI). |
| API contract | Spec-first `api/openapi.yaml`; server interfaces and Swift client are **generated** from it | One contract for two languages (DRY across the boundary). |
| Hosting | AWS Lightsail VM + Docker Compose (Caddy, backend, Postgres); HTTPS on the static IP, domain optional | Cheapest simple setup; Caddy obtains a Let's Encrypt IP-address certificate automatically (section 19). |
| Blob storage | `BlobStorage` interface; local-disk implementation (Docker volume) for MVP | Replaceable by S3 without touching the domain (DIP, spec 48). |
| Async AI processing | DB-backed job table + in-process worker on virtual threads | No Redis/Kafka/Celery (YAGNI, spec 4). Survives restarts. |
| Submission waiting model (spec 50) | **Option B: the backend owns the wait** | Watch can press Send while the iPhone is still uploading; no client-side polling-then-resubmit. |
| OpenAI conversation state | `store: false`, backend-built context | Backend stays the source of truth; retention stays under our control (spec 32, 38, 47). |
| Result delivery | Polling / long-polling; APNs slot reserved | Free account has no push (PI 1.2). |
| Multi-user readiness | `user_id` on every row, device tokens in DB; no registration UI | Cheap now, expensive to retrofit later. |

## 3. Shared Swift modules (`CopilotKit` package)

```
CopilotKit
├── CopilotAPI     # Generated by swift-openapi-generator from api/openapi.yaml (transport DTOs + client).
│                   # Generated sources are committed; refresh with apple/scripts/generate-api.sh
│                   # (a build plugin fails when Xcode builds iOS + embedded watchOS in one build).
└── CopilotCore    # Hand-written, platform-neutral
    ├── Domain/        # Conversation, Message, DraftSummary, AttachmentStatus, RequestState ...
    ├── Mapping/       # DTO -> domain mapping (the only place that knows DTO shapes)
    ├── Services/      # CopilotService protocol + live implementation over CopilotAPI
    ├── Auth/          # KeychainTokenStore
    └── Observation/   # RequestObserver (long-poll / later push), see section 10
```

Layering (spec 52): generated DTOs -> `CopilotCore` domain models -> SwiftUI views with `@Observable` view models. Views never see DTOs.

Platform-specific code stays in the app targets and is **not** shared (YAGNI):

- iOS only: `CameraCapture`, `PhotoImport`, `ImageNormalizer` (resize/JPEG), `UploadManager` (background `URLSession`).
- Watch only: Watch views, haptics.

`CopilotService` is a protocol (DIP). This is justified now: Phase 1 runs the Watch app against an in-process `MockCopilotService` with no backend at all, and tests use the same seam.

## 4. Backend architecture

Single Spring Boot application, package-by-feature:

```
com.aicopilot
├── api/            # Generated OpenAPI interfaces + controllers, RFC 9457 problem responses
├── auth/           # Bearer device-token filter; resolves userId
├── conversation/   # Conversation, Message, active conversation
├── draft/          # Draft, Attachment, upload handling, hourly purge of expired image bytes
├── submission/     # AiRequest state machine, SubmissionService (idempotent submit)
├── processing/     # Worker: claims jobs, calls AiEngine, persists assistant message
├── ai/             # Port: AiEngine; ContextBuilder; ResponseMode registry
│ └── openai/       # Adapter: OpenAiEngine (openai-java)
├── storage/        # Port: BlobStorage; LocalDiskBlobStorage
├── usage/          # AI usage ledger and cost report (GET /v1/usage)
└── config/
```

Ports (interfaces) exist only where there is a concrete second implementation (DIP where it pays):

- `AiEngine`: `OpenAiEngine` (production) and `FakeAiEngine` (tests, spec 58).
- `BlobStorage`: `LocalDiskBlobStorage` (MVP) and S3 (later).
- `Clock` (java.time): deterministic tests of timeouts and retention.

Everything else is concrete classes (KISS).

## 5. Persistence model (PostgreSQL)

All ids are UUIDs. Ids for attachments and idempotency keys are **generated by clients**, which makes retries idempotent by primary key.

```
users            (id, created_at)
devices          (id, user_id, name, platform, token_hash, created_at, last_seen_at, revoked_at)
user_settings    (user_id PK, active_conversation_id)

conversations    (id, user_id, title, title_source[PLACEHOLDER|AI|USER], mode[GENERAL|DANISH_EXAM],
                  status[ACTIVE|ARCHIVED], created_at, updated_at)

drafts           (id, user_id, conversation_id, text, state[OPEN|FROZEN|CONSUMED],
                  version, created_at, updated_at)
  UNIQUE (conversation_id) WHERE state = 'OPEN'   -- one editable draft per conversation; a FROZEN draft
                                                  -- belongs to its request, so a new question can start meanwhile

attachments      (id, user_id, draft_id, position, source[CAMERA|PHOTO_LIBRARY], mime_type,
                  byte_size, sha256, width, height, state[PENDING|UPLOADED|FAILED],
                  failure_reason, blob_key, created_at, uploaded_at, purged_at)
  UNIQUE (draft_id, position)

messages         (id, user_id, conversation_id, seq, role[USER|ASSISTANT], text,
                  draft_id NULL UNIQUE,            -- user message <- consumed draft (attachments via draft_id)
                  ai_request_id, suggested_actions JSONB, response_mode, model, usage JSONB, created_at)
  UNIQUE (conversation_id, seq)                    -- stable ordering

ai_requests      (id, user_id, conversation_id, draft_id, idempotency_key,
                  state, user_message_id, assistant_message_id UNIQUE,
                  attempt_count, locked_until, last_error_code, response_mode,
                  created_at, updated_at, started_at, completed_at)
  UNIQUE (user_id, idempotency_key)
  UNIQUE (draft_id) WHERE state <> 'CANCELLED'    -- a cancelled Send returns its draft, which can be sent again

ai_usage         (id, user_id, ai_request_id UNIQUE, model, input_tokens, cached_input_tokens,
                  cache_write_tokens, output_tokens, created_at)
                                                  -- no FK to conversations: the cost report survives deletion
```

Notes:

- Attachments never move between owners. A user message references its consumed draft, and its attachments are that draft's attachments ordered by `position` (spec 27).
- Immutability (spec 8): services reject any mutation of a draft that is not `OPEN` and of its attachments. Tests enforce it.
- Image bytes live in `BlobStorage`, not in the database (spec 48).

## 6. REST API contract (v1, summary)

Authentication: `Authorization: Bearer <device token>` on every request. Errors: `application/problem+json`.

| Method & path | Purpose | Idempotency |
|---|---|---|
| `GET /v1/home` | **One-call snapshot for the Watch main screen**: active conversation, draft summary (counts by state, text), latest request state, last answer preview. Supports `ETag` / `If-None-Match`. | read |
| `GET /v1/conversations?cursor=` | List conversations | read |
| `POST /v1/conversations` | Create; body contains client-generated `id` | PK |
| `PATCH /v1/conversations/{id}` | Rename; a user title is final (the AI never replaces it) | natural |
| `DELETE /v1/conversations/{id}` | Delete with messages, drafts, requests and image bytes (spec 47); the active conversation moves to the most recent remaining one | natural |
| `PUT /v1/active-conversation` | Set the active conversation (synced between devices) | natural |
| `GET /v1/conversations/{id}/messages?after=` | Messages in `seq` order | read |
| `GET /v1/conversations/{id}/draft` | Get-or-create the current draft | natural |
| `PATCH /v1/drafts/{id}` | Set text; requires `If-Match: <version>` (no silent overwrite between devices) | version |
| `PUT /v1/drafts/{id}/attachments/{attachmentId}` | **Register** an attachment (metadata: position, mime, size, sha256, source). Creates `PENDING`. | PK |
| `PUT /v1/attachments/{id}/content` | **Upload bytes** (raw body). `PENDING/FAILED -> UPLOADED` after the checksum is verified. | PUT |
| `DELETE /v1/drafts/{id}/attachments/{attachmentId}` | Remove (draft `OPEN`, or request `BLOCKED`) | natural |
| `POST /v1/drafts/{id}/submit` | Header `Idempotency-Key`; body `{ text? }`. Freezes the draft and creates an AI request. Returns `202` + request. | key + `draft_id` unique |
| `GET /v1/requests/{id}?waitSeconds=0..25` | Request state; long-poll until the state changes or timeout | read |
| `POST /v1/requests/{id}/cancel` | Cancel Send (`WAITING`/`BLOCKED` only); the draft returns to `OPEN` | natural |
| `POST /v1/requests/{id}/retry` | Retry a `FAILED` inference of the latest question. Same user message, **no new message**. | natural |
| `GET /v1/usage` | Tokens and estimated cost: today, this month, all time (prices configured on the backend) | read |

Why two steps for attachments (register, then upload): the backend learns about each page **before** its bytes arrive. This lets the Watch show "Uploading 2/3" and lets the backend refuse to run on an incomplete set (Invariant 6). The upload itself is a plain file body, which is what an iOS background session supports (PI 10.4).

A text question from the Watch is the same pipeline: `submit(draftId, text)` on the current (empty) draft. **One submission path for all message types (DRY)** and a single network call for the Watch.

## 7. Draft state machine

```
          add/remove attachment, edit text
               ┌──────┐
               ▼      │
 (created) ─► OPEN ───┘
               │ submit
               ▼
             FROZEN ──── cancel request ───► OPEN   (photos and text kept; a newer OPEN draft is merged into it)
               │ all attachments UPLOADED (same transaction as UserMessage creation)
               ▼
            CONSUMED   (immutable; a new OPEN draft is created lazily)
```

Submit validation: the draft must have text or at least one attachment. An empty draft returns `422`.

## 8. Attachment state machines

Server (authoritative):

```
 register ─► PENDING ── bytes stored + sha256 ok ──► UPLOADED
                │  ▲
   client error │  │ re-upload (retry)
   / timeout    ▼  │
               FAILED
```

- `PENDING` older than `ATTACHMENT_UPLOAD_TIMEOUT` (for example 10 minutes) becomes `FAILED` with reason `upload_timeout`. This covers a force-quit iPhone app (PI 10.2).
- A retry is `PUT /content` with the same id. It cannot create a duplicate (spec 44).

iOS client (local presentation state): `local -> registering -> uploading(progress) -> uploaded | failed`. The server state wins on refresh.

## 9. AI request state machine

```
 submit ─► WAITING_FOR_ATTACHMENTS ── all UPLOADED ──► QUEUED ──► PROCESSING ──► COMPLETED
               │        ▲                         (UserMessage       │  ▲
   attachment  │        │ retry ok / removed       created here)     │  │ lease expired
   FAILED      ▼        │                                            │  │ (worker crash)
             BLOCKED ───┘                                            ▼  │
               │ cancel                                            FAILED ── retry ──► QUEUED
               ▼
           CANCELLED (draft -> OPEN)
```

Mapping to spec 36: `waitingForAttachments` = WAITING/BLOCKED, `submitted` = QUEUED, `processing`, `completed`, `failed`.

- If the draft is already fully uploaded at submit time, `WAITING -> QUEUED` happens inside the submit transaction.
- The `UserMessage` is created **only** at `-> QUEUED`, atomically with `Draft -> CONSUMED`. A message therefore never exists with a missing page.
- `BLOCKED`: the user chooses Retry upload / Remove attachment / Cancel Send (spec 26).

**Idempotency and races (spec 37):**

- Same `Idempotency-Key` again (network retry): returns the same request (`200`).
- Watch and iPhone press Send at the same time (different keys): the `UNIQUE(draft_id)` constraint lets exactly one win. The loser gets `409` with the existing request, so the client keeps its typed text and tells the user "already sent from another device". **Input is never silently discarded** (spec 43).
- Worker crash during an OpenAI call: the lease expires and the job is retried. `assistant_message_id UNIQUE` guarantees **one assistant message**. An honest caveat: exactly-once delivery to an external API is impossible. In a crash window OpenAI can be called twice; `attempt_count` records it.

## 10. Synchronization strategy

- **Backend = single source of truth** for conversations, messages, drafts, attachments and states (spec 38).
- Clients refresh on: app activation, after each own mutation, and by long-polling an active request.
- The Watch main screen needs **one call** (`GET /v1/home`) with `ETag`, so polling is cheap.
- Draft text edits use optimistic locking (`If-Match`) to avoid silent overwrites between devices.
- **WatchConnectivity**: only for one-time provisioning of the device token from iPhone to Watch (PI 8.2, 8.3). Never used as storage.
- Client abstraction `RequestObserver` hides how completion is detected:
 - `LongPollRequestObserver` (MVP, H1);
 - `BackgroundSessionRequestObserver` (H2/H3, if Phase 2 validation shows benefit);
 - an APNs-based observer if a paid account appears later.
 Adding one does not change views or services (OCP).

## 11. Background-processing strategy

| Where | Mechanism |
|---|---|
| Backend | Owns all AI work. `submit` returns `202` immediately. The worker claims `QUEUED` rows with `SELECT ... FOR UPDATE SKIP LOCKED`, sets a lease (`locked_until`) and runs on virtual threads. An in-process signal after commit wakes the worker instantly; a periodic sweep (every few seconds) is the safety net and also handles lease expiry and upload timeouts. |
| iPhone uploads | Background `URLSession` (non-discretionary), `uploadTask(fromFile:)`. The normalized JPEG is written to the app container first. Relaunch events reattach to the session by identifier. |
| iPhone submit | A small foreground request. The iPhone can be locked right after the `202` (Invariant 7). |
| Watch | No background work in MVP beyond H1. H2 is evaluated in Phase 2. |

```
Camera screen (full screen, opens directly)
 ┌───────────────────────────┐
 │        viewfinder         │
 │                           │
 │ [thumb][thumb][thumb]  3  │  <- pages in the current draft (tap = review)
 │   [Done]   (◉)   [Photos] │

      shutter (or volume / Camera Control via AVCaptureEventInteraction)
             ▼

- Confirm never triggers inference (Invariant 2).

- Image normalization happens on the iPhone: smaller uploads, faster Send. Its parameters are tuned in Phase 3 against OCR quality (PI 11.3).

Home (NavigationStack root)

 │    "3 photos ready ✓" | "Uploading 2/3…" | "1 photo failed - fix on iPhone"
 │    [Send]  [Add text & Send]

```

- After Send, the app navigates to Conversation with a processing indicator. The answer appears in place with `.notification` haptic (PI 9.3).
- Typography sized for 49 mm; no fixed dimensions assumed, so smaller watches keep working.

**Decision (Q1, confirmed by the owner):** when the draft holds attachments, text entered on the Watch (via **Ask** or **Add text & Send**) becomes the text of that draft, and the draft is sent together with the photos. Text stays optional: **Send** without text is the primary path, because the images are usually self-explanatory; the default image instruction applies (spec 28). A text-only message is sent only when the draft has no attachments.

## 15. OpenAI integration boundary

```
processing.Worker
   └─► AiEngine (port)                    generate(AiContext) -> AiReply | AiError
          └─ OpenAiEngine (adapter)       only class that imports com.openai.*

ai.ContextBuilder                         builds AiContext from the conversation (backend owns context, spec 32)
ai.ResponseMode registry                  WATCH_CONCISE now; LANGUAGE_TUTOR etc. later (OCP, spec 34)
```

- **Context**: last N messages of the conversation (configurable). User messages carry their images in order, as base64 data URLs read from `BlobStorage`. Purged images become the text placeholder `[image no longer available]`.
- **Image-only messages**: the default instruction (spec 28) is added by `ContextBuilder` at inference time only. The stored message text stays `null`.
- **Instructions**: loaded from resource files per `ResponseMode` (`prompts/watch_concise.md`): answer first, no filler, keep numbering, 30-100 words, **answer in Russian, quote source-language words verbatim**.
- **Structured output**: JSON Schema, strict: `{ text: string, suggestedActions: [{title, prompt}] (max 3) }`. Parsed and validated in the adapter. Clients receive typed fields only (spec 51).
- **Config (env)**: `OPENAI_MODEL`, `OPENAI_REASONING_EFFORT`, `OPENAI_IMAGE_DETAIL`, `OPENAI_TIMEOUT`, `OPENAI_MAX_RETRIES`, `OPENAI_STORE=false`. No model names in code (spec 33).
- **Model choice**: benchmark `gpt-6-sol` vs `gpt-6-astra` in Phase 2-3 on real exam pages for latency and accuracy. Speed is UX priority #1.
- **Deferred**: streaming (YAGNI for MVP); Files API `file_id` instead of base64 if payload latency proves significant.

## 16. Testing strategy

**Backend unit tests** (JUnit 5, `FakeAiEngine`, fixed `Clock`), mapping to spec 58:

| Invariant | Test |
|---|---|
| Draft with multiple attachments / text only / images only | `DraftServiceTest` |
| Failed attachment blocks submission | `SubmissionServiceTest.failedAttachmentBlocks` |
| Uploading attachment prevents inference | `...pendingAttachmentWaits` (no call to `FakeAiEngine`) |
| All uploaded -> submission proceeds | `...allUploadedQueues` |
| Duplicate Send -> one message, one AI request | `...sameKeyReturnsSameRequest`, `...concurrentSubmitsOneWins` |
| Attachment removal updates the draft | `DraftServiceTest.removeReindexes` |
| Submitted message immutable | `...consumedDraftRejectsMutation` |
| Follow-up belongs to the same conversation | `ConversationFlowTest` |
| Attachment order preserved | `ContextBuilderTest.imagesInPositionOrder` |
| Upload timeout -> FAILED | `AttachmentTimeoutTest` (fixed Clock) |

**Backend integration tests**: Spring Boot + Testcontainers PostgreSQL. Covers draft -> submit -> message, multi-image, idempotency under concurrency (parallel submits), processing transitions, lease expiry. The OpenAI adapter is tested against a local HTTP stub (request shape and error mapping). **No test calls the real OpenAI API.** A manual `smoke` profile exists for that.

**Swift**: Swift Testing for `CopilotCore` (DTO mapping, derived UI states such as "Uploading 2/3"). The UI is verified manually with the device checklist.

**Contract**: CI regenerates server interfaces and the Swift client from `api/openapi.yaml`; a build break means drift.

## 17. Security and privacy

- HTTPS only (Caddy + Let's Encrypt). No plaintext HTTP (spec 46).
- The OpenAI key exists only in the backend `.env` (git-ignored).
- Device tokens: 256-bit random, stored as a hash on the server. Revocable per device.
 Interim (Phase 2): the Watch build reads host + token from the git-ignored `Signing.local.xcconfig` via Info.plist.
 Phase 5 replaces this with pairing through the iPhone and Keychain storage.
- Logs: structured JSON with `requestId`, `conversationId`, `draftId`, `messageId`, `aiRequestId`, durations and OpenAI status. **No message text, no image content, no secrets** (spec 59).
- Retention: original images are purged after `IMAGE_RETENTION_DAYS` (default 30). Deleting a conversation deletes its blobs immediately (after the database commit). OpenAI side: 30-day abuse-monitoring logs, no application state with `store: false` (PI 11.6). Not yet explained inside the apps (spec 47 asks for it in a settings screen).

## 18. Multi-user readiness (future, not built now)

Built now because it is cheap: `user_id` on every row and in every query; device tokens bound to users.
Not built (YAGNI): registration, account UI, roles, per-user quotas.
To be required later: a paid Apple Developer account (TestFlight), a privacy policy, per-user OpenAI cost limits.

## 19. Deployment

- Lightsail VM (2 GB RAM is enough for JVM + Postgres), Docker Compose: `caddy`, `backend`, `postgres`. Volumes: `pgdata`, `blobs`.
- TLS without a domain: Lightsail static IP + a Let's Encrypt **IP-address certificate** (generally available since 2026-01-15, only with the `shortlived` profile, 160-hour lifetime, renewed automatically by Caddy). Sources: [Let's Encrypt announcement](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability), [LE profiles](https://letsencrypt.org/docs/profiles/), Caddy issue [#7399](https://github.com/caddyserver/caddy/issues/7399) (IP issuance with `shortlived` fixed, closed 2026-04-25).
- To verify in Phase 2: ATS accepts the IP-SAN certificate on iOS and watchOS. Fallback: buy a domain (about $14/year) and switch the A record; the clients only change the base URL.
- The static IP must stay attached to the instance, because the clients store the base URL.
- Verified 2026-09-28 on 18.197.218.28: certificate issued (issuer Let's Encrypt YE2, SAN `IP Address`).
  Caddy needs `default_sni` because TLS clients send no SNI for IP addresses.
- Backups: Lightsail automatic snapshots (daily).
- Local development: the same `docker-compose.yml`. Phase 1 needs no backend (in-app mock).
